# RoleBridge private-pilot review — 18 October 2026

Scope: reviewed the existing static HTML, app/model/matching/role modules, PDF/DOCX readers and vendored dependencies, development server, CI and browser tests before extending the product. This is an engineering review, not a penetration test, legal opinion, certification or finding of GDPR compliance.

## Priority and release scope

The highest-priority task was safe continuity and useful outcomes: replace plaintext persistence, complete the existing journey and measure whether users find the next action useful. OpenAI remains disconnected. No real candidate records were used for development or tests.

This release supports a small, voluntary **device-only pilot**. “Create private workspace” is local signup, **not a hosted account or server authentication**. Workspace creation does not require email, password recovery information, identity documents or billing details. The current interview flow collects no contact fields; optional legacy CV contact fields remain local in older workspaces until deleted. A hosted multi-user launch is a separate release with the gates below. Do not describe this pilot as having verified users, server authorisation, cloud sync or production-grade account recovery.

## Data flow and threat boundary

Browser loads app/readers from GitHub Pages → user provides CV → text extracted in memory → user selects reviewed evidence → local rule-based comparisons and dashboard. Explicit workspace creation enables encrypted local autosave. Returning user enters password locally to decrypt. Raw file, full extracted text, password and key are excluded from serialization. No CV is sent to GitHub by the app. GitHub receives ordinary hosting request metadata, including IP addresses, and users can navigate voluntarily to external employers.

A locked vault limits exposure from casual access to browser storage. It does not protect an unlocked workspace, malicious extensions, keyloggers, OS compromise, browser/device backups or malicious same-origin code. All repositories on `cmcgerty88.github.io` share an origin: path names do not isolate localStorage. Other site code on that origin can read/delete ciphertext or interfere with the app. Use a dedicated controlled origin for a broader public service. Meta CSP cannot supply frame-ancestors or HSTS headers; a future host must set appropriate response headers and frame protection. Do not accept arbitrary untrusted HTML/assets onto that origin.

No rate-limit claim for local password guesses: someone possessing ciphertext can attempt offline guesses. There is no recovery service. Strong unique password, device security, explicit limits and encryption are essential. Automated tests exercise ciphertext tampering, wrong password, retention, migration and tab conflicts; an independent security review is still needed before material expansion.

## UK/EU GDPR and pilot operations

Local processing reduces disclosure; it does not automatically remove legal obligations. Before collecting recruitment contacts, research notes or feedback externally, the organiser must identify the controller and contact route, purpose, lawful basis per activity, recipients/processors, retention and rights arrangements in an actual participant notice. The app intentionally does not invent a controller identity or claim that a storage checkbox is a GDPR lawful basis for every activity. The checkbox is the user's choice to use local persistence.

For an initial assisted pilot, participants operate their own device and may decline saving/feedback. Do not request their CV, password, encrypted backup or screenshots of private screens. Avoid recording screens. Do not put research notes, personal data or support reports into public GitHub issues. If collecting minimal voluntary pilot feedback directly, provide the organiser's real contact and notice first; keep recruitment contact details separately, use participant codes and delete identifiable notes under an agreed schedule (suggested 30 days after pilot analysis). Record withdrawals and honour them for data the organiser controls.

Users can inspect/edit their entries, clear local data and make an encrypted portable copy. For data held externally, provide access, rectification, erasure, restriction, objection and portability processes as applicable; explain how to complain to the ICO (UK) or relevant EU supervisory authority, including Ireland's DPC. Assess UK GDPR/DPA 2018 and EU GDPR territorial scope, special-category data risks, age policy, accessibility, ePrivacy/PECR storage obligations and whether a DPIA is required. Local necessary storage, hosting metadata and research consent must be considered separately. Recommendations here do not decide hiring or send applications; reassess profiling/automated-decision obligations if that changes.

## Gates before hosted accounts, server CV handling or OpenAI

1. Name the operator/controller and publish an accurate notice with purpose, lawful basis, retention, rights/contact and processor/transfer disclosures. Conduct a DPIA screening, document the result and address redundancy-related vulnerability. Obtain relevant professional advice for deployment scope.
2. Select a hosted identity provider and UK/EU-appropriate data region/processor terms. Implement verified sessions with Secure/HttpOnly/SameSite cookies, CSRF protection where applicable, session expiry/revocation, recovery and abuse controls. Do not implement “auth” as a localStorage login flag.
3. Deny-by-default database/object storage, per-user ownership enforced on the server and in database policies. Test cross-user reads/writes/deletion, forged identifiers, expired sessions and privilege escalation. No service/admin keys or long-lived bearer credentials in frontend code.
4. Minimise server data: retain reviewed structured facts instead of CV files by default. If uploads become necessary, private buckets, bounded parsing in isolated workers, content validation, malware controls, short-lived access and automatic expiry. No CV contents or tokens in logs, analytics, errors, URLs or support tooling.
5. HTTPS and appropriate security headers on a dedicated origin; managed encryption at rest, key rotation/access controls, incident/breach process, monitored dependency updates, encrypted backups and tested deletion/expiry including backup lifecycle and rights requests.
6. Only then consider OpenAI: explicit user-triggered processing, minimised/redacted payload, server-only key, provider agreement/data retention/training/region/transfer review, deletion handling, prompt-injection controls and human review. Never send whole CVs by default. Publish exactly what is sent and why. Keep disabled until these controls and pilot demand justify it.

## Application document release addendum

The same review now covers `application-data.mjs`, `application-content.mjs`, `application-ui.mjs`, `interviews.mjs` and `document-export.mjs`. No account, server or AI processing was introduced. Additional reviewed data is limited to CV name/contact fields, career/education/training text, up to five vacancy-specific drafts, and bounded candidate-written interview notes. It is included in the existing encrypted autosave/expiry/deletion flow only when the user has enabled that flow; the UI and storage notices explain it. Raw CV content is still excluded unless the user explicitly chooses to copy or type relevant facts into reviewed fields.

CV identity/contact fields are omitted for an anonymised export. PDFs/DOCX/TXT are intentionally **unencrypted candidate-triggered exports**, a new exception to the earlier encrypted-backup-only release. The builder gives an explicit notice and requires CV fact review before export. These files must be deleted separately and should not enter the public repository; generated filename patterns are ignored by Git. Interview exports contain questions and practice notes, not contact fields. No profile preferences, unrelated vacancies or raw CV text are added. No automated submission occurs.

PDF generation uses pinned, locally served pdf-lib/fontkit and a bundled licensed font; DOCX uses the existing fflate writer with escaped XML and a minimal text-only package. There is no remote conversion service, external image/font request or document-content URL. PDF rendering is capped at 30 pages; unsupported characters cause an actionable error instead of silently dropping text. The PDF output has selectable text and character mappings; no claim is made that it is fully tagged PDF/UA or that every ATS will parse it correctly. Plain-text and Word alternatives are available.

Question selection uses explicit role choice and up to three user-reviewed advert excerpts. It does not infer protected characteristics or fabricate an answer. Role scope is the existing 12-role library with an explicit general fallback. Draft refresh and question changes preserve existing edits until the user explicitly confirms replacement; source-change hashes detect profile/advert changes and are not authentication controls. Test fixtures are synthetic, including Unicode names and adversarial markup.
